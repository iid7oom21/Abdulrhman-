## أولًا: العيوب التي أُثبتت في المصدر الأصلي (`createLegacyPlayer`)

في النموذج الأصلي المبسط:

```js
async function play() {
  await audio.play();
  playing = true;
}
```

لا تتغير قيمة `playing` إلى `true` إلا **بعد** تسوية `Promise` الخاص بـ `audio.play()`. وقد أثبتنا عبر الاختبارين الأولين في `player-controller.test.mjs` عيبين رئيسيين بالنتائج الفعلية وتسلسل الأحداث:

### 1. الضغط على تشغيل ثم الضغط على `toggle()` قبل اكتمال `Promise` الأول
- **تسلسل الأحداث الفعلي في المصدر الأصلي**:
  1. `legacy.play()` يستدعي `audio.play()#1`، لكن `playing` تبقى `false` طالما أن الوعد معلّق.
  2. المستخدم يضغط `legacy.toggle()` بنية الإيقاف، فيفحص المشغل `if (playing)` فيجدها `false`، فيستدعي `play()` **للمرة الثانية** (`audio.play()#2`) بدل استدعاء `pause()`.
  3. عند تسوية الوعدين (`resolve#1`, `resolve#2`)، ينتهي المشغل في الحالة `{ index: 0, playing: true }` مع `playCalls = 2` و `pauseCalls = 0`، رغم أن آخر أمر للمستخدم كان الإيقاف.
- **سجل الأحداث المسجل في الاختبار**:
  `src:track-01 -> play()#1 -> play()#2 -> resolve#1 -> resolve#2`

### 2. بدء تشغيل الأغنية الأولى ثم اختيار أغنية أخرى (`select(1)`) قبل اكتمال `Promise`
- **تسلسل الأحداث الفعلي في المصدر الأصلي**:
  1. `legacy.play()` يبدأ طلب تشغيل الأغنية `0`، وتظل `playing === false` أثناء انتظار التسوية.
  2. `legacy.select(1)` يقرأ `const resume = playing` فيحصل على `false`، فيستدعي `pause()` ويغيّر `index = 1` و `audio.src = tracks[1].src`، لكنه **يتجاهل** تشغيل الأغنية الجديدة لأن `resume === false`.
  3. عندما ينجح وعد `audio.play()` القديم الخاص بالأغنية `0` متأخرًا، ينفذ السطر `playing = true`، فتصبح حالة المشغل `{ index: 1, playing: true }` كذبًا، رغم أن الأغنية `1` لم يُستدعَ لها `play()` أبدًا (`playCalls = 1`).

## ثانيًا: كيف يمنع الإصلاح تأثير النتائج القديمة (`Stale Promises`)

في `createPlayer(audio, tracks)` داخل `player-controller.mjs`:

1. **معرّف العملية المتزايد (`operationId`)**:
   - كل أمر يغيّر حالة التشغيل (`play`, `pause`, `select`, `dispose`) يزيد العداد `operationId += 1`.
   - عند استدعاء `play()`، يُحفظ المعرف المحلي `const currentOp = operationId`.
   - عندما يُسوى وعد `audio.play()` (سواء بالنجاح `then` أو بالرفض `catch`)، يتحقق المتحكم أولًا من:
     ```js
     if (disposed || operationId !== currentOp) {
       return false;
     }
     ```
   - إذا كان المستخدم قد ضغط إيقافًا، أو بدّل الأغنية، أو أطلق طلب تشغيل أحدث، أو استدعى `dispose()`، فإن `operationId` يكون قد تغيّر، فتُهمل نتيجة الوعد القديم تمامًا دون المساس بالحالة الأحدث.

2. **منع استدعاءات `play()` المكررة أثناء الانتظار**:
   - إذا كانت الحالة `loading` ويوجد طلب جارٍ (`activePlayPromise`)، فإن استدعاء `play()` المباشر يعيد نفس الوعد الجاهز دون إطلاق استدعاء `audio.play()` إضافي.
   - أما الضغط على `toggle()` أثناء `loading` فيقرأ `desiredPlaying === true` ويترجمه فورًا إلى أمر إيقاف (`pause()`).

## ثالثًا: كيفية تمثيل حالات المشغل (`State Model`)

يفصل المشغل المصلح بين ثلاث طبقات مستقلة في `getState()`:

| الحقل | النوع | الدلالة |
|---|---|---|
| `status` | `'paused' \| 'loading' \| 'playing' \| 'error' \| 'disposed'` | الحالة الصريحة للمشغل في اللحظة الحالية |
| `desiredPlaying` | `boolean` | **نية المستخدم**: `true` منذ لحظة طلب التشغيل (`loading` أو `playing`)، و `false` عند الإيقاف أو الخطأ أو التخلص (`dispose`) |
| `pending` | `boolean` | **انتظار بدء التشغيل**: `true` فقط أثناء انتظار تسوية `audio.play()` (`status === 'loading'`) |
| `playing` | `boolean` | **التشغيل المؤكد**: `true` فقط بعد نجاح `audio.play()` للعملية الأحدث (`status === 'playing'`) |
| `index` | `number` | فهرس الأغنية الحالية (`0` إلى `tracks.length - 1`) |
| `error` | `Error \| null` | كائن الخطأ عند رفض `play()` أو رميه استثناءً متزامنًا (دون إعادة محاولة تلقائية) |
| `disposed` | `boolean` | `true` بعد استدعاء `dispose()` وفك مستمع `ended` وإيقاف الصوت |
| `operationId` | `number` | رقم العملية الحالية لعزل التسويات المتأخرة |
| `trackCount` | `number` | عدد الأغاني المستخرج ديناميكيًا من `tracks.length` (14 في بيانات التجربة) |
| `src` | `string` | مسار الأغنية المختارة حاليًا |

### سلوك الحالات الحدية:
- **القائمة الفارغة أو غير الصالحة**: يرمي `createPlayer(audio, [])` خطأ `RangeError` واضحًا، ويرمي `TypeError` إذا لم تكن القائمة مصفوفة أو خلا أي مدخل من `src` نصي غير فارغ.
- **الفهرس غير الصحيح في `select(nextIndex)`**: أي قيمة غير صحيحة (`-1`, `14`, `1.5`, `NaN`, `'2'`, `null`, `undefined`) ترمي `RangeError` قبل تنفيذ أي تعديل، فتبقى الأغنية الحالية وحالة التشغيل دون أي تغيير أو انقطاع.

## خامسًا: حدود الاختبارات والفصل بين منطق التحكم واختبار المتصفح

- **ما تثبته اختبارات `FakeAudio` (`player-controller.test.mjs`)**:
  - صحة آلة الحالة (`State Machine`) وعزل الوعود غير المتزامنة (`Promises`) وترتيب التسويات مهما تأخرت أو تداخلت.
  - عدم ضياع نية المستخدم عند التبديل السريع بين الأغاني الأربع عشرة أو الضغط المتتالي على `toggle()`.
  - الالتفاف الصحيح من الأغنية 14 إلى الأغنية 1 عند حدث `ended`، والتنظيف الكامل عبر `dispose()`.
- **ما لا تثبته اختبارات `FakeAudio` ويحتاج إلى متصفح وأجهزة فعلية**:
  - وجود ملفات الصوت الحقيقية أو سلامة ترميزها عبر الشبكة (`HTTP 200/206 Range Requests`).
  - سياسات التشغيل التلقائي (`Autoplay Policy` / `NotAllowedError`) التي يفرضها المتصفح قبل تفاعل المستخدم (`User Gesture`).
  - سلوك `HTMLMediaElement` و `AudioContext` الفعلي على متصفح Safari في iOS/iPadOS (مثل قيود `audio.volume` وإطلاق أحداث `waiting` و `stalled` و `AbortError` عند تغيير `audio.src`).
